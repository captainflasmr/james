** 0.80.0 — <2026-08-16>

=C-x r l= opens the bookmarks in a buffer — a persistent =*Bookmarks*= list like the =*Ibuffer*= — while =C-c o= / =M-l o= stay the fuzzy picker.

- =C-x r l= now opens (or switches to) a =*Bookmarks*= buffer, the persistent sibling of the =C-c o= / =M-l o= bookmark picker, mirroring Emacs's =bookmark-bmenu-list= the same way =C-x C-b= mirrors ibuffer: a table under a header and dashes ruler — the bookmark's name in a 20-wide column (long names eliding with =...=), the bookmarked path taking the rest of the row — with a footer of the total count (=2 bookmarks=). It behaves like any buffer: it stays open in the list, =C-x o= / =C-x b= move around it, and the listing re-reads itself whenever a bookmark is set or reloaded (a =bookmark_list_gen= generation counter, the bookmarks' twin of =buffer_list_gen=), so a row can never be stale. In it, =n= / =p= (arrows too) move, Enter jumps to the row's bookmark in this window (the =*Bookmarks*= stays open, like a dired), =g= re-reads the listing (Emacs =revert-buffer=), =q= / =C-g= closes, and =C-s= / =C-r= search the table like any buffer. The =C-c o= / =M-l o= completing-read picker is untouched — type to filter, Enter jumps — and the =*Bookmarks*= shows in the =*Ibuffer*= as =Bookmarks= mode. The native and =x86_64-windows= cross builds compile.

** 0.79.0 — <2026-08-15>

The buffer / bookmark / recent-file pickers dock at the bottom of the display icomplete-vertical-style, the dired buffer ends with a visible trailing newline, and the =*Ibuffer*= truncates by default.

- The pickers (=C-x b=, =C-c o=, =M-l l=) render at the bottom of the display like Emacs's icomplete-vertical-mode / minibuffer: the windows shrink up to make room, their modelines sitting just above the candidate list, the current candidate highlighted in reverse video, and the typed filter in a prompt row beneath the candidates with the cursor at its end. The buffer or dired stays visible above while picking — the candidates no longer merge into the buffer's text. An idle hint ("type to filter, Enter opens, C-g closes") stands in for the filter when nothing is typed; the isearch prompt keeps its label, query and lazy count.
- A dired buffer now ends with the trailing newline an Emacs dired has: =M->= (or =n= past the last entry) rests the selection on the empty final line, visible like a file buffer's final line, and copies of the listing (=C-c b=, =C-x h= + =M-w=) carry the final line break. The mirror buffer's trailing empty line is never drawn (the listing renders from the dired's entries) and never matched by isearch; every operation that indexes the selected entry (mark, copy, rename, delete, compress, duplicate, reveal, open) treats the trailing line like =".."= — a safe no-op.
- The =*Ibuffer*= (=C-x C-b=) truncates by default, like the =*grep*= / =*files*= / =*occur*= results buffers — one buffer per row, however long the name, with =[truncate]= in its modeline (=M-z= toggles soft wrap).
- The native and =x86_64-windows= cross builds compile.

** 0.78.0 — <2026-08-15>

=C-x E= opens the native file manager at the current context, and =C-x T= opens a new native terminal window in its directory — from a dired, from a file buffer, from anywhere.

- =C-x E= reveals the current context in the file manager: the selected entry while browsing a dired (=".."= never), the file itself in a file buffer, the working directory when the buffer has no file. A directory opens the manager at it; a file opens its folder — with the entry selected on macOS (=open -R=), in Nautilus / Dolphin (=--select=) / Nemo / Caja (a file argument selects), and plainly in Explorer (which takes a bare directory argument; its =/select= form would need cmd's raw command-line handling) and Thunar. Linux/BSD deliberately skips the freedesktop =xdg-open= for the reveal: the =inode/directory= MIME default can be hijacked by an unrelated application (EasyTag's desktop file claims it — seen in the wild), so the first installed manager is picked by name instead — nautilus, thunar, dolphin, nemo, caja, pcmanfm, pcmanfm-qt — with =xdg-open= only as the directory-only last resort (it has no "reveal").
- =C-x T= opens a *new* native terminal window in the current context's directory — the dired's own while browsing, the file's directory otherwise, the working directory with no file: Windows Terminal where installed (=wt.exe -d=; a new =cmd.exe= window via PowerShell's =Start-Process= is the fallback, both built into Windows), Terminal.app on macOS (=open -a Terminal=), and the first installed desktop emulator on Linux/BSD (gnome-terminal, konsole, xfce4-terminal, kitty, alacritty, wezterm, then the generic =x-terminal-emulator= / =xterm= with a cd-and-exec shell). The directory is absolutized before it goes out, so a relative dired path (say =.=) survives the round trip to the tools' =cd= / =--working-directory= handling. It is the sibling of =C-x j=, which takes over this terminal instead of opening a new one.
- Both spawn detached — through a backgrounding shell (=sh -c 'exec "$@" &'=, reaped immediately), so a foreground app (alacritty, xterm, a single-instance file manager) never blocks the editor while it runs. The binary is checked on the PATH first, since a backgrounded exec failure is silent; a missing file manager or terminal reports =Failed to open file manager= / =No terminal emulator found= on the modeline. The native and =x86_64-windows= cross builds compile.

** 0.77.0 — <2026-08-14>

=C-c j= / =C-c k= land focus on the right pane again — no more frozen cursor after flipping layouts.

- Winner-mode's focused-pane index was recorded in post-order by =serializePane= (the counter ticked after recursing into the children) but looked up in pre-order by =paneAt= (check at entry, tick before recursing), so the two never agreed: after every =C-c j= / =C-c k= the focus landed on the wrong pane — often the root split itself, whose =buf_idx= defaults to 0. Buffer 0 is frequently a read-only buffer (the welcome screen, a dired), so the cursor wouldn't move, no cursor was drawn (no leaf matched the internal-node focus) and the editor looked frozen — most visible when flipping back and forth quickly, which cycled through snapshots until one landed on a read-only buffer. =serializePane= now assigns the index in pre-order, matching =paneAt= and the pre-order node list =deserializePane= already reads, so the recorded focused index and the lookup agree. The node-list layout is unchanged (it was always pre-order); only the index counter's tick moved from the end of the function to the start. The native and =x86_64-windows= cross builds compile.

** 0.76.0 — <2026-08-14>

=C-c j= / =C-c k= no longer go stale after a dired switch or an ibuffer kill, and a restore can no longer dangle the root.

- Two buffer-switch paths were invisible to winner-mode history, so =C-c k= afterwards jumped to a stale layout: =C-x d= / =C-x m= (open a dired) and the =*Ibuffer*= =X= kill confirm now record the pre-change layout first, like every other switch-buffer path (=C-x b=, the pickers, =C-x C-f=), so =C-c j= steps back past them and the redo branch is abandoned. The ibuffer kill records once before the multi-kill (each =closeBuffer= inside it rebases the saved snapshots, but the pre-kill state must be on the undo stack to return to).
- =restoreSnapshot= used to destroy the old pane tree before building the new one, so an allocation failure mid-build returned with the root pointing at freed memory — a use-after-free on the next frame. The new tree is now built first and the old one destroyed only once the new one exists, so a failed restore leaves the old tree intact. Restored buffer indices are also clamped to the live buffer list at the restore boundary (defense-in-depth: the kill-time rebase already covers the known shrink path, but the render path indexes =buffers[buf_idx]= unguarded, so a missed rebase or a future shrink path can no longer crash there). The native and =x86_64-windows= cross builds compile.

** 0.75.0 — <2026-08-14>

Scroll-lock stays at 60 FPS on a hundred-thousand-line buffer.

- =C-x l='s scroll-lock mode used to binary-search the whole buffer for the top line that keeps the cursor on its locked row, re-wrapping every line on every step — an O(n log n) pass per frame that dropped well below 60 FPS on a large wrapped buffer. The viewport now caches a prefix sum of the per-line visual (wrapped) heights on the buffer, keyed by a generation counter (bumped on every edit), the pane width, the soft-wrap setting and the gwidth method, so the search is O(log n) per frame instead: a handful of array lookups, each O(1). The cache is rebuilt only when the lines, the width, the wrap setting or the method change (a one-time O(n) pass after an edit or a resize), and ordinary scrolling — holding =C-n= / =C-p= in scroll-lock — never touches it. The non-scroll-lock path is unchanged (it was already viewport-bounded), and a cache that can't be grown falls back to the original search, so nothing regresses. The cache fields are plain types on =Buffer= (the gwidth method stored as a =@intFromEnum= =u8= tag), so the data model stays free of any vaxis dependency, the same discipline the rest of =Buffer= follows. Verified: the native and =x86_64-windows= cross builds compile.

** 0.74.0 — <2026-08-14>

The theme follows the terminal's actual background color, queried by OSC 11.

- james now asks the terminal for its exact background RGB at startup (and after a =C-x j= shell swap) with an OSC 11 query (=ESC]11;?ESC\\=), and sets the dark/light theme from the reply's luminance (Rec. 601: =0.299R + 0.587G + 0.114B=) — a more precise read than the =.color_scheme= dark/light boolean, so the dim chrome (=dimStyle=, the unfocused modelines, the line-number gutters, the inactive tab labels) is only used where it actually reads against the background. The query is safe to send unconditionally: a terminal that doesn't answer OSC 11 simply never replies, and the existing =.color_scheme= path (CSI 997n) remains the fallback for the initial read and the live-update channel when the terminal's own theme switches at runtime — both just set =theme_dark=. Verified end to end: a light terminal background turns the dim chrome plain, a dark one keeps it dim, and the =x86_64-windows= cross build still compiles.

** 0.73.0 — <2026-08-14>

The =*Ibuffer*='s =X= kill asks before discarding unsaved changes.

- =X= in the =*Ibuffer*= (kill the marked buffers) now asks when any marked file buffer has unsaved changes, exactly like =C-x k=: the modeline shows =Kill the marked buffers, N modified without saving? (y kills them, n keeps them, C-g cancels)= — =y= kills everything marked including the modified files without saving, =n= kills the clean ones and keeps the modified (=Modified buffers kept= is reported even when nothing was killed), =C-g= / Esc cancels entirely, and any other key is ignored. A marked set with no modified buffers kills straight away as before. The kill itself (largest index first, the =*Ibuffer*= re-found and re-focused, the listing rebuilt) was extracted into one shared helper used by both the prompt's answers and the direct path.

** 0.72.0 — <2026-08-14>

Focus reporting: losing the terminal's focus can no longer stick the Windows Alt state (or an armed repeat map) on forever.

- james enables DECSET 1004 focus reporting while it owns the terminal (startup and after a =C-x j= shell; disabled again for the shell and on exit). The terminal's CSI I / CSI O focus reports — plain sequences, so Windows Terminal's ConPTY passes them through like any other — arrive as a new =focus_out= event, and the handler clears the two sticky states a lost key-up would otherwise jam permanently: the Windows sticky-Alt flag (=windows_pending_alt=, which re-applies Alt to the next key until the Alt key-up arrives — an =Alt+Tab= while holding Alt drops that key-up, so every following key would be typed as =M-<key>= forever) and the armed repeat map (=C-x o= / =C-c j= stepping, which the same lost key-up would leave jumping windows). Verified end to end: after arming the =C-x o= repeat, a focus report clears it, and the next =n= types into the buffer instead of moving windows; both the native and the x86_64-windows cross builds compile and run.

** 0.71.0 — <2026-08-14>

Saves are atomic: the file is written to a temp beside it and renamed over, so a crash or power cut can never truncate it.

- =C-x C-s= (and the quit-confirmation save) no longer writes the file in place: the text goes to a =<name>.james-tmp= file in the same directory first — the same filesystem, so the final rename replaces the target atomically on both POSIX and Windows — and the temp is then renamed over the original. A crash, power cut or killed terminal mid-write can no longer leave the real file truncated or half-written: it is always either the old content or the new. The temp keeps the original's permissions (a =0755= script stays executable after a save) and is fsynced before the rename, so a power cut after the rename can't leave the target pointing at unsynced data; a failed save cleans the temp up. Saving through a symlink resolves the link first and writes to its target, so the link survives the rename (renaming over the link itself would have replaced it with a plain file). New files, =LF= / =CRLF= round-trips and the =[modified]= flag behave exactly as before.

** 0.70.0 — <2026-08-14>

=C-g= cancels a background grep / find instantly, even while the tool is silent.

- C-g (and starting a new search over an old one) now kills the running tool directly: the worker records the child's id (the pid on POSIX, the process handle on Windows) right after spawning it, and the main loop's cancel path kills it by that id — SIGKILL on POSIX, =NtTerminateProcess= on Windows. Before, cancel relied on the worker noticing the flag at its next read of the tool's output — a tool that produces no output at all (a quiet =rg= / =grep= still scanning, a =find= walking a slow tree) would leave the worker blocked in the read forever, so C-g did nothing until the tool happened to finish on its own. The direct kill closes the pipe (the tool dies, its stdout write end goes away), the worker's read returns, and the run finalizes as cancelled immediately — verified at ~10ms from the C-g keypress. The worker still kills the child itself on its own path, so nothing is double-killed; the id is cleared once the child is reaped.

** 0.69.0 — <2026-08-14>

The =%= =m= regexp is strict Emacs syntax (a bare =(= / =)= / =|= is a literal), and CRLF files keep their line endings on save.

- The =%= =m= dired regexp now follows Emacs strictly: =\(...\)= is the only group form and =\\|= the only alternation — a bare =(= =)= =|= is a literal character, exactly as in Emacs regexps, so a name like =archive_(1).zip= or =md|txt= is matchable as-is (previously both the raw and the escaped forms opened groups / alternated, making literal parentheses impossible). The prompt, README and the Dired unit tests were updated; nothing else changes — =.=, =[...]=, the =*= =+= =?= quantifiers, anchors and the =\\d= =\\w= =\\s= escapes behave as before.
- Editing a CRLF (Windows / DOS) file no longer silently rewrites it with LF line endings on save: the buffer remembers the file's line-ending style at load (=Buffer.eol=), strips the =\\r= from each line for editing as before, and writes =\\r\\n= back on =C-x C-s=, so a CRLF file round-trips byte-for-byte and never dirties every line for git. New files and files with LF endings are untouched. (This was the review item about CRLF → LF normalization.)

** 0.68.0 — <2026-08-14>

The directory header line stays unnumbered (it is not an entry) and sits at the gutter's edge, aligned with the entries' mark column; the cursor lands after the gutter on the selected entry's name as usual. The modeline shows =[linum]= while on — =Dired: <path> [linum]= — and the setting is per-buffer like soft wrap, so each dired remembers its own. ** 0.67.0 — <2026-08-14>

=C-x C-b= opens the =*Ibuffer*=, Emacs's ibuffer: every buffer in a table, with marks and kill-marked.

- =C-x C-b= (Emacs =list-buffers= / ibuffer) opens a persistent =*Ibuffer*= buffer — the sibling of the transient =C-x b= picker — listing every open buffer in an Emacs-style table: the =MRL= mark / read-only / lock column, then the name, size, mode and filename columns, and a footer mirroring Emacs's =N buffers ... M files, no processes= summary. The mode column reads like Emacs's (=Dired by name= and the other dired sorts, =Grep= / =Files= / =Occur= / =Home= for the special buffers, =Fundamental= for a file), read-only buffers show =%= in the R column, long names elide with =...=, and the default sort puts the starred buffers first by name (=s= toggles to the buffer-list order). It is a real buffer: it stays open in the list, shows in any window, and the listing rebuilds itself whenever a buffer opens or closes, so a stale row can never be acted on. =n= / =p= (and arrows) move, Enter opens the row's buffer in the window (the =*Ibuffer*= stays open, like a dired), =m= / =u= mark and unmark rows with a =*= in the M column, =U= unmarks everything, =t= toggles all marks, =X= kills the marked buffers — largest index first so the kills can't shift underfoot, a modified file buffer kept, the ibuffer re-found and re-focused after — =g= re-reads the listing, =q= / =C-g= closes, and =C-s= / =C-r= search the table like any buffer. The cursor lands on the current buffer when the ibuffer opens, and a rebuild keeps the selection on the same buffer by name.

** 0.66.0 — <2026-08-12>

=C-c r= forces a full re-render of the frame, washing out stray characters the terminal has picked up.

- =C-c r= (the =C-c= family's free =r=, for refresh) makes the next frame a full repaint: vaxis's =queueRefresh= skips the frame-to-frame diff and writes every cell afresh, so any garbage the terminal has accumulated — random characters appearing on screen, most often noticed on Windows, where the console can mangle or drop output from the background grep / find tools and the cp / robocopy / PowerShell helpers — is overwritten and the display is clean again. The modeline reports =Display refreshed= so the press is visible, and the message lingers until the next keypress like any transient status. One keypress, anywhere in the editor (file buffers, direds, the results lists), and the layout is untouched.

** 0.65.0 — <2026-08-12>

Dired marks by regexp: =%= =m= prompts for a pattern and marks every entry whose name matches.

- =%= =m= in dired (Emacs =dired-mark-files-regexp=, the same =%= prefix =m= key) prompts for a regexp and marks every entry whose name matches it, the modeline reporting how many were marked (=Marked 3 files=). The regexp is a small Emacs-flavoured one: =^= =$= anchors, =.= any character, =[...]= / =[^...]= classes with ranges, the greedy =*= =+= =?= quantifiers, =|= and Emacs =\\|= alternation, =(...)= and =\(...\)= groups, and the =\\d= =\\D= =\\w= =\\W= =\\s= =\\S= escapes plus any escaped literal (=\\.=, =\\*=, ...) — everything but backreferences and interval counts, which names rarely need. ** 0.64.0 — <2026-08-12>

Grep and find run in the background with a live progress readout, the file list's =n= / =p= type into the filter, and =C-z n= shows line numbers.

- =C-c g= (grep), =C-c f= (find files) and the =g= re-runs no longer freeze the editor while the tool scans: the search runs on its own thread, and the modeline shows its live status — a spinner, the matches (grep) or files (find) counted so far, and the elapsed time — while the editor stays fully responsive for editing, navigating and everything else. =C-g= cancels a running search (the tool is stopped and the modeline reports =Search cancelled= or =Find cancelled=); when the run lands, the results buffer is built exactly as before — the old =*grep*= / =*files*= buffer replaced or re-mirrored, focus moving to the results for a fresh search and staying put for a =g= re-run — and the status line clears. - The M-key chords work on Windows again: Windows Terminal's ConPTY reports an =Alt+J= press as a plain =j= — the ALT bit is dropped from the key record — so =M-j= and friends scrolled the dired or typed into a filter instead of moving. The bare Alt key-down, which Windows does deliver as its own record, is now remembered and re-applied to the key that follows, with the Alt key-up clearing it again, so =M-j= / =M-k= / =M-J= / =M-K= / =M-<= / =M->= behave on Windows exactly as they do elsewhere.

** 0.63.0 — <2026-08-10>

Isearch remembers the last search string, and =M-o= jumps straight to a window.

- Isearch remembers the last search, like Emacs: after a search finishes, a fresh =C-s= (or =C-r=) with an empty query repeats the previous search from the cursor — jump to the top with =M-<= and press =C-s= to find it again from the start — and the first character typed replaces the remembered string instead of gluing onto it, the same prefill rule as the grep / occur prompts. It works from file buffers, direds and the results buffers, and joins the other window keys in the help and README.
- The window-navigation repeat keys are trimmed: =M-n= / =M-p= are single moves again, while =C-x o= keeps its =n= / =p= / =o= repeat and =C-c j= / =C-c k= keep their =j= / =k= layout stepping.

- vaxis's own =std.log= output (the "(vaxis): kitty keyboard capability" startup notices) is suppressed via =std_options= — stderr shares the terminal, so that chatter used to be painted on the editor screen.

** 0.9.0 — <2026-08-01>

Home screen and file-less startup.

- james now starts without any file arguments: instead of a usage message it opens a home screen — a big block-letter =james= logo, a one-line description, and a keybinding cheat sheet — shown in a file-less buffer named =*welcome*=.
- The home screen is a real buffer, so movement, search, and every =C-x= command work on it; =C-x d= from there opens dired rooted at the current directory and is the fastest way in.

** 0.8.0 — <2026-08-01>

Nested window splits.

- =C-x 2= and =C-x 3= now split the focused pane instead of appending to a flat strip: =C-x 2= splits horizontally (panes stacked above / below), =C-x 3= vertically (panes side-by-side). Because each split subdivides the focused pane, directions nest freely — a vertical split inside a horizontal one, and so on, same as real Emacs.
- The split model is a binary tree of panes (the =Pane= struct in =main.zig=) rather than a flat list of buffer indices with one global split direction; each node divides its children either horizontally or vertically and the tree is rendered recursively into child windows.
- =C-x o= moves focus to the next pane, wrapping around; =C-x 0= deletes the focused pane, giving the space to its sibling; =C-x 1= collapses back to a single pane.
- Each pane keeps its own buffer; opening a file from =C-x b= / =C-x d= replaces only the focused pane's buffer. Panes draw their own compact modeline, and only the focused one shows the cursor.
- =C-x d= dired now renders inside the focused pane rather than taking over the whole screen, so any other split panes stay visible while browsing; choosing a file swaps dired for the newly opened buffer and the standard layout is restored.
- Splits are capped at 16 panes; further split requests are ignored.

** 0.7.0 — <2026-07-31>

Directory browser (dired).

- =C-x d= opens a directory listing in the editing pane, rooted at the directory of the current buffer's file (or =.= if the buffer has no file). It's another "mode branch" at the top of the key-dispatch loop in =main.zig= — the same shape as incremental search, the buffer-switch prompt, and the quit-confirmation, not a redesign.
- While in dired: =n= / =C-n= / ↓ and =p= / =C-p= / ↑ move the selection, =^= goes straight to the parent directory (the =^= shortcut in real dired), Enter descends into a directory or opens the selected file as a buffer, and =C-g= / =q= leaves dired and returns to the buffer.
- Opening a file from dired reuses the same open-or-switch path as =C-x b= / =C-x C-f=: if a buffer already visits that exact path it's switched to, otherwise the file is loaded fresh as a new buffer.
- Entries are sorted with =..= first, then case-insensitive by name; directories and files are interleaved rather than grouped, and directories are shown with a trailing =/=. Hidden (dot) files are listed too.
- =src/Dired.zig= holds all directory state (path, entries, selection, scroll, navigation) with no knowledge of the terminal or of buffers — the same portability split as =Buffer.zig=; =main.zig= just wires keys and rendering.
- =Dired.parentOf= doesn't resolve to a canonical absolute path: once a plain =dirname= can't go further up a relative path, further "up" requests just accumulate literal =..= components, which the OS resolves fine. It returns null only at the absolute filesystem root, where there's genuinely nowhere to go.

** 0.6.0 — <2026-07-27>

Multiple buffers.

- =C-x b= and =C-x C-f= both prompt for a filename on the status line and do the same thing: Enter switches to it if already open (matched by exact path, whitespace-trimmed), or loads and opens it fresh otherwise. =C-g= / Escape cancels.
- A single "open or switch by path" command covers both cases for a minimal editor, where real Emacs splits these (=C-x C-f= opens by path, =C-x b= switches by buffer name with separate completion).
- When more than one buffer is open, the status line shows =(current/total)= so it's visible at a glance.
- Every open buffer is its own heap-allocated =Buffer= stored in =main.zig= as =std.ArrayList(*Buffer)= — a list of pointers, not values, so appending (opening a new file) can't invalidate earlier pointers when the list's backing array reallocates.
- Only the kill ring lives above the buffer list, shared by every buffer, matching real Emacs.
- No way to close a buffer yet (=C-x k= in real Emacs) — buffers accumulate for the life of the process; a natural next step.

** 0.5.0 — <2026-07-27>

Unsaved-changes confirmation on quit.

- =C-x C-c= asks "Save file ... before exiting?" on the status line when the buffer has unsaved changes: =y= saves and quits, =n= quits without saving, =C-g= (or Escape) cancels the quit and returns to editing.
- Any other key is ignored while the prompt is up, rather than risk a stray keystroke accidentally choosing for you.
- A save that fails (disk full, permissions, etc.) is still silently swallowed, same as =C-x C-s= today — worth real error reporting eventually.
- Known caveat: quitting relies on libvaxis's normal shutdown path, which sends a terminal status query to wake its background input thread; real terminal emulators answer this automatically, but the exit path could not be fully confirmed from inside a sandboxed test harness lacking a real terminal emulator. Closing the terminal window or =C-c= from another shell always works as a fallback.

** 0.4.0 — <2026-07-27>

Incremental search.

- =C-s= / =C-r= for incremental search forward / backward.
- While searching: typing extends the query, =C-s= / =C-r= again jumps to the next / previous match, Backspace shrinks the query, =C-g= cancels back to the start, and Enter (or any other key) confirms and leaves the cursor at the match.
- A search with no match shows "Failing I-search" and stops moving the cursor until the query is backspaced back to something that matches.
- Search never crosses a line boundary and wraps around the buffer when it runs off either end.
- The =isearch_active= branch at the top of the key-dispatch loop in =main.zig= is the "mode" plumbing — when =M-x= arrives, it will be a second branch of the same shape, not a redesign.

** 0.3.0 — <2026-07-27>

Undo.

- =C-x u= restores whole-buffer snapshots taken before each edit.
- Coalesces a run of the same kind of edit (a burst of typing, a run of backspaces) into a single undo step, so undoing a word just typed is one keypress, not one per character.
- Switching to a different kind of edit — or moving the cursor — starts a new undo step.
- No redo yet: undo is a one-way trip back through history, and it does not (yet) clear the =[modified]= flag even if it lands back on the exact text loaded.
- Undo history, the mark, cursor position, and the dirty flag are all separate per buffer; only the kill ring is shared.

** 0.2.0 — <2026-07-27>

Kill ring and yank.

- =C-space= sets the mark; the region between mark and point is shown in reverse video as the cursor moves, and clears on kill, copy, or dropping the mark.
- =C-k= kills to end of line (or kills the newline at end of line); =C-w= kills the region (point to mark); =M-w= copies the region without deleting; =C-y= yanks the most recent kill.
- Consecutive =C-k= / =C-w= / =M-w= presses append to the same kill instead of overwriting it, same as real Emacs; typing or moving the cursor starts a fresh kill.
- The kill ring is shared across all open buffers, so text killed in one file can be yanked into another.
- =Buffer.mark= is a plain snapshot, not a self-adjusting marker, so it can go stale if the buffer is edited between setting mark and using the region — acceptable for now.

** 0.1.0 — <2026-07-27>

Initial release.

- A very minimal, Emacs/MicroEmacs-inspired text editor written in Zig on top of [[https://github.com/rockorager/libvaxis][libvaxis]].
- Basic cursor movement: =C-f= / =C-b= / =C-n= / =C-p= and arrow keys for right / left / down / up, =C-a= / =C-e= for start / end of line.
- Editing: =C-d= / Delete deletes forward, Backspace deletes backward, Enter inserts a new line.
- Save and quit: =C-x C-s= saves, =C-x C-c= quits.
- Each filename on the command line opens as its own buffer; the first is shown initially. First run fetches libvaxis automatically; =zig build --fetch= pre-fetches dependencies for offline builds.
- Cross-compiles with no extra toolchains or Docker: confirmed working on =x86_64-windows=, =aarch64-macos=, =x86_64-linux-musl=, and native with =-Doptimize=ReleaseSmall=; binaries land in =zig-out/bin/=.
- Architecture split: =src/Buffer.zig= holds all text state (lines, cursor, load/save, edit and movement operations) with no knowledge of the terminal or other buffers; =src/main.zig= is the only platform-facing file (terminal setup, event loop, key dispatch, rendering) — the same portability discipline MicroEmacs used in the 1980s.
- Requires Zig 0.16.0 exactly, pinned in =build.zig.zon=.
